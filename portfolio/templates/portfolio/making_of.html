APIs — Decisões e Processo

🏗️ API Interna — Django Ninja

app: API · montada em /api/

Decisão

Foi criada a app API com dois modelos: APIKey (gestão de chaves de acesso) e Noticia (recurso principal exposto). A framework escolhida foi o Django Ninja por gerar documentação automática (Swagger UI em /api/docs) e integrar naturalmente com o ORM do Django.

Autenticação

Implementada a classe AuthAPIKey(APIKeyHeader) que valida o header X-API-Key contra a base de dados, verificando se a chave existe, está ativa e não expirou. Os endpoints de leitura são públicos; criar, editar e apagar requerem chave válida.

Recursos expostos

Além de Notícias, foram adicionados endpoints para UnidadesCurriculares, Projetos e Tecnologias — todos com CRUD completo, filtragem por campo (ex: ?ano=, ?categoria=) e paginação (?page= + ?page_size=).

🌐 API do Colega — ProgrammingLanguage

colega: joaocarmona22301968 · acesso em /api_endpoint/

Decisão

O consumo da API externa foi implementado server-side com a biblioteca requests, em vez de JavaScript/fetch no cliente. Desta forma, a chave da API fica protegida no servidor e a lógica de integração fica centralizada nas views Django.

Implementação

Foram criadas 4 views em portfolio/views.py: listar, criar, editar e apagar linguagens. Os formulários são HTML puro (sem forms.py), lendo os dados via request.POST.get() e enviando-os para a API do colega como JSON com o header X-API-Key.

Campos do recurso

id, name, slug, typing, compiled, year_created, creator, latest_version, difficulty, open_source, website
